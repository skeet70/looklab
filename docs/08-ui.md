# 08 — UI

There are no accounts and no login. Browsing, matching, verification and previews are anonymous and upload nothing. Contributing creates a pseudonymous passkey at the first upload. Seeders, moderators and admins should use hardware-backed passkeys or security keys.

## 1. Site map

```
/                       Landing: pick body → pick look → match. Look previews carousel.
/bodies                 Browse/search bodies
/bodies/:body           Body page
/looks                  Browse/search looks (native families + LUT-defined)
/looks/:look            Look page (version selectable)
/compare?a=&b=          Compare any two looks / realizations
/match                  Match flow (body, firmware, target, capability)
/match/r/:permalink     Result (computed client-side from pinned versions)
/verify                 Verification loop (local)
/recipes                Recipe leaderboards per look × body
/bounties               Wanted data
/contribute             Contribution ladder (creates a credential at first upload)
/status/:token          My contributions (capability token): per-image status, impact, withdrawal
/passkeys               Help: passkey options (phone QR flow, security keys, password managers), status link recovery (sign in with your passkey to re-issue the link)
/propose                Proposals: body, schema change, firmware interface, LUT look
/proposals/:id          Proposal page: summary, evidence, confirm, moderator thread
/mod                    Moderation queue (moderators); endorsement queue (seeders)
/admin                  Grants of seeder/moderator/admin (admins; also `looklab-cli admin`)
/log                    Public audit log (page + JSON); public lists of grants and endorsements
/pattern/:seed          Full-screen phone pattern (no chrome)
/about/privacy          Privacy, payload format, CLI alternative, source links
```

## 2. Public pages

**Body page:**
- Make/model, epochs, capabilities.
- **Mapping status:** `fixture-backed` or `provisional` (no donated fixture yet).
- **Input transform confidence:** source + anchoring count + tier.
- **Realization notes** in plain language, e.g. "renders ~0.5 EV darker in DR200 than the reference body".
- **Control schema** per epoch, with differences between epochs.
- **Native looks:** a card per sim with status (provisional / rooted / published), data volume, coverage, cross-body agreement.
- Bounties and recipes for this body.

**Look page:**
- Name, kind, version picker, status, `wb_policy`, license/attribution (LUT-defined).
- **Preview:** canonical scenes (§5) with A/B against any other look.
- **Diagnostics** from [02 §7](02-color-pipeline.md) with uncertainty bands and hatched unsupported regions.
- **Provenance:** bodies and epochs, root sessions with seeder badges, anchor version, changelog, gate results. A notice appears if the version relied on a since-revoked root admission, or was produced by a revert.
- **Weak spots,** linking to bounties.
- An artifact hash with a "matches version manifest" indicator.

**Compare:** any two of look / look version / realization. Diagnostic overlays, the ΔE distribution, the region map, the one-line summary.

## 3. Match flow

1. **Your body:** search, or detect from a dropped JPEG (EXIF read locally). Pick the firmware version; it maps to an epoch fuzzily, with a provisional warning.
2. **Target:** any Look. Optional emphasis: balanced / skin / landscape / product.
3. **Capability:** stock controls / firmware interface profile (filtered to the body) / generic LUT export.
4. **Result:**
   - **Settings card** ([04 §4](04-matching-and-export.md)): base sim and controls in menu order and wording, including EC/WB shift where useful; predicted ΔE with confidence; residual summary; unreachable regions; a "your body vs. target" preview; verify; save as recipe (creates a credential if needed).
   - **Artifact:** download, validation report (including per-CCT results for single-illuminant profiles), profile used, unsupported-region note.
5. **Permalinks** pin every model version used ([04 §4](04-matching-and-export.md)), so a result always reproduces.

## 4. Contribute and propose

**Contribute:** a walkthrough built around the ladder ([07](07-contribution.md)):
1. **Drop files or a folder.** Local pairing, metadata read, grouping, coverage preselection. Shows pairs found, unpaired files with reasons, and groups.
2. **Confirm groups:** native vs. recipe (with target); settings from makernotes, editable where unreadable.
3. **Local processing,** with the live coverage map.
4. **Payload inspector** ([06 §7](06-privacy-and-payload.md)) → confirm with the passkey (one gesture per batch) → proof-of-work runs → upload.
5. **Status link + next rung,** each step skippable.
6. Feedback arrives asynchronously at `/status/:token`.

Leaving keeps what's done. Drafts persist locally (IndexedDB) for resuming. Because browser storage can be evicted, the UI shouldn't depend on drafts surviving.

**Propose (photographer-friendly):**
- Proposals are **shown in menu terms**, not YAML. For example: "adds Reala Ace to X-T5 firmware 2.0+", "Highlight tone goes −2 to +4 in half steps".
- **Ask in menu terms** ("Which film simulation was this shot with?"). The app **infers makernote tag/value mappings** from several labeled files, so nobody has to pick tags.
- The **schema validator runs in the browser** (`looklab-schema` compiled to WASM, the same code CI uses), so errors are caught before submission.
- **Fixture donation:** an explicit per-file opt-in to donate a file as a test fixture, with consent recorded in the fixture manifest. Mappings without a fixture ship as `provisional`.
- **Confirmations are evidence, not votes.** "My camera shows this menu too" attaches the confirmer's parsed, whitelisted tag values from their own file. Moderators decide.
- **LUT-defined looks:** require a license declaration (own work, or licensed for redistribution under the data license) plus attribution.
- **Firmware interface profiles:** for firmware authors. Submitted as YAML or through a form; a round-trip report from the pipeline simulator is generated at submission.
- Proposals are rate-limited per credential and require proof-of-work.
- **Discussion** is limited to the proposer and moderators ("request info"). There's no open forum.

## 5. Launch previews (canonical scenes)

- 8–12 project-owned scenes (with model releases): skin (several), foliage, sky, neutral interiors, saturated products, a night/high-DR scene.
- Stored as scene-linear XYZ (D65-adapted), ~2 MP, half-float, static assets.
- Rendered client-side (WASM, or a baked 33³ LUT in a shader), output to sRGB.
- **"On your body" view:** target vs. predicted achievable realization, with a difference toggle.

## 6. Moderation

- **Queue items:**
  - body/schema/mapping proposals;
  - interface profiles;
  - LUT looks;
  - worker-generated epoch and look split proposals (evidence attached);
  - failed release gates;
  - serial-reuse flags and bursts of new credentials on one Look;
  - reverts in progress.
- **Seeders' queue:** endorsement nominations (high-reputation new-tier contributors, with their accepted data summarized) and root-admission candidates (anchored sessions from endorsed contributors).
- Each item shows its evidence and actions (approve / reject / request info) with a required reason.
- **Look-level actions:** re-anchor (with reason), and **revert**: "revert to version N, exclude credential(s) K, refit" ([05 §8](05-trust-and-integrity.md)).
- Every decision and action is written to the audit log ([05 §11](05-trust-and-integrity.md)).
- Moderators work with a short-lived session opened by a passkey assertion. Seeder actions (endorse, admit to root) and admin grants require a fresh assertion each time.
- Approved changes to community data produce a new **community data snapshot**, validated by CI with the same validator and fixture checks.

## 7. General UI notes

- Show uncertainty wherever a number appears.
- Plain language first; details one click away.
- Accessible plots: color-blind-safe palettes, labels and patterns, never color alone.
- Mobile: browsing, look pages, the settings card and the pattern page must work well. Large-folder processing may want a desktop, but should degrade gracefully.
